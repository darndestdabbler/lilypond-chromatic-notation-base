### H1. The runner can harvest a stale SVG, so a broken render passes
- **Severity:** high
- **Where:** `tools/run_tests.py:394-403`, together with the render going into `tests/` at `:509` and `render_dir` at `:338`
- **Defect:** After LilyPond runs, the runner takes `{base}.svg` if it exists, then `{base}-page1.svg`, then any `{base}*.svg`. It never checks that the file was written by this run. 2.24 renders go into `tests/`, beside the tracked `tests/{base}.svg`. 2.26 renders go into the ignored, persistent `out/lilypond-2.26/`.
- **Failure scenario:** A change makes a test score need a second page. LilyPond 2.24 and 2.26 both name multi-page SVG output `{base}-1.svg` and `{base}-2.svg`; `-page1` is never produced. The runner finds the tracked, stale `tests/{base}.svg` first and harvests it. The assertions pass and the drift check passes, because the stale SVG is the baseline. The same happens with a leftover `out/lilypond-2.26/{base}.svg`.
- **How verified:** In the worktree I removed `#(set! cnb:keysig-style 'none)` from `tests/keysig-none.ly`, which is a real regression: a key signature now gets engraved. I also added `\pageBreak g1`. The result was `RESULTS: 2 passed, 0 failed`, exit 0, `SVG: ...tests\keysig-none.svg`. The fresh `keysig-none-1.svg` and `keysig-none-2.svg` were left untracked.
- **Fix:** Delete `{base}*.svg` from the output folder before rendering, or compare modification times against the run's start, and fail if not exactly one fresh SVG appears. Handle `-1.svg` explicitly, or fail on multi-page output.

### H2. `cnb:duration-category` misclassifies tuplets and double-dotted notes, so the wrong notehead repetition is engraved
- **Severity:** high
- **Where:** `cnb/utils.ly:331-336`
- **Defect:** The category is computed from the duration's full length, including dots and the tuplet scale factor (`log2(denominator) - floor(numerator/2)`). It should come from the duration log. Category 1 draws 2 noteheads, category 0 draws 4 and category 2 or above draws 1 (`cnb/stencils.ly:158`). The category also selects the config and the stem attachment.
- **Failure scenario:**
  - A triplet half note (1/3) gets category 2, so it is drawn as a single quarter-style notehead.
  - A triplet whole (2/3) gets category 1, so it is drawn as a half.
  - A double-dotted quarter (7/16) gets category 1, so it is drawn as a doubled half notehead.
  - A double-dotted half (7/8) gets category 0, so it is drawn as a whole.

  This breaks the README's claim (line 55) that "half notes render as 2 noteheads, whole notes as 4".
- **How verified:**
  - `probe/dur.ly` gives identical wrong categories on 2.24 (`duration-length`) and 2.26 (`ly:duration->number`). The 2.24/2.26 shim itself is consistent: both return the same exact rationals.
  - `probe/tup.ly`, harvested: a plain half has bbox.w 1.5, i.e. a double head. The triplet halves `nh-2-*` have bbox.w 1.0 although data-duration is 1. The double-dotted quarter `nh-3-0.000` has bbox.w 1.5 although data-duration is 2.
  - The unit suite skips this function. `test-unit.ly:163` prints "SKIP: duration-category requires LilyPond Duration objects", but `ly:make-duration` works fine in test-unit context.
- **Fix:** Use `(max 0 (min 3 (ly:duration-log dur)))`, which also removes the need for the version shim. Add unit tests built with `ly:make-duration` for dotted, double-dotted and tuplet durations.

### H3. The dot-avoidance callback throws augmentation dots several staff spaces away from notes on ledger lines
- **Severity:** high
- **Where:** `cnb/dots.ly:69` and `:112`, installed at `cnb/layout.ly:128`
- **Defect:** For a notehead on a ledger line, the callback sets the Dots grob's `staff-position` to the notehead's absolute position ±1. The Dots grob is already positioned relative to the notehead, which carries CNB's `Y-offset`, so the notehead's offset is counted twice.
- **Failure scenario:** `c'2.` on default CNB places the dot 6.5 staff spaces below the note, `e'''2.` places it 8.5 above, and so on for every dotted note on a ledger line. Notes inside the staff are not affected.
- **How verified:**
  - `probe/dots-on.ly` against `probe/dots-off.ly` (callback disabled with `\override Dots.before-line-breaking = ##f`), harvested.
    - With the callback: `nh-1` is at -6.0 staff spaces from the centre and `dt-1` at -12.5; `nh-3` is at 8.0 and `dt-3` at 16.5.
    - Without it: the dots sit at -5.5 and 8.5, i.e. next to the notes.
  - The PNGs (`probe/dots-on-png.cropped.png`, `probe/dots-off-png.cropped.png`) show the dots visibly detached.
  - 2.26 gives the same result.
  - No test score has a dotted note on a ledger line; all 11 dots in `joy-to-the-world` are inside the staff.
- **Fix:** Shift relative to the notehead, for example by setting the Dots `Y-offset` to `dodge-dir × 0.5 × staff-space`, or drop the callback, since LilyPond's default already moves the dot off the line. Add an integration test with a dotted ledger-line note.

### M1. Stem attachment reads the global config cache at layout time, so a later key change rewrites earlier notes' stems
- **Severity:** medium
- **Where:** `cnb/stems.ly:60-63` (called from `NoteHead.stem-attachment`, `cnb/layout.ly:71`)
- **Defect:** `cnb:stem-attachment` runs at layout time, after the whole score has been engraved. It calls `cnb:lookup-config`, which reads `cnb:config-cache`, and that cache holds the last key seen. `cnb/noteheads.ly` already documents this hazard for x-offset and captures that value at acknowledge time. Attachment was not given the same treatment.
- **Failure scenario:** A config whose `attachment` depends on `key` (the API passes `key` to the procedure for exactly this kind of use) is used in a piece with a mid-piece `\key` change, or in a multi-staff score with different keys. Every note gets the attachment of the last key processed.
- **How verified:** `probe/att-*.ly` uses a config that picks `low-side` when F# is in the key. Measure 1 in C major is identical in both files; only one file adds `\key g \major` in measure 2. The measure-1 stems moved from x=14.132 to 13.132 and grew from h 3.5 to 3.95.
- **Fix:** Resolve the attachment record in the notehead acknowledger, as is already done for `cnb-x-offset`, and store it on the grob. Alternatively, store the key's pitch classes on the grob and look the config up from them.

### M2. The harvester ignores the geometry of `<circle>`, `<polygon>` and `<text>`, so off-key rings, dots and beams are invisible to assertions and to drift detection
- **Severity:** medium
- **Where:** `tools/harvest_svg.py:155-171` (`_get_local_position`) and `:297-299` (`compute_bbox_deep` falls back to a single point). `extract_path_data_deep` hashes `<path>` only.
- **Defect:**
  - A circle counts as its centre point and its radius is ignored.
  - A polygon counts as its transform origin; `points` is ignored, so every beam has `bbox` w=h=0 and no `path_hash`.
  - Text has zero extent, so the `'text` clef in `clef-text-size` has bbox 0×0.
- **Failure scenario:** An off-key `'ring` mark (`cnb/off-key.ly:117`, a circle) is added or removed, and the harvest is byte-identical, so neither an assertion nor the baseline can see it. The `'dot` mark's extent is short by its radius. Beam shape (slope, thickness, length) is never captured; drift catches beam changes only through side effects on positions.
- **How verified:** I rendered `off-key-coexistence` with `'ring` and with `#f` marks (`probe/ok-ring.ly`, `probe/ok-none.ly`). `harvest_differences` between the two harvests returned `[]`, although one SVG contains a `<circle>` and the other does not. Every `bm-*` element in the tracked baselines has bbox w=0.
- **Fix:** Include the circle (cx±r, cy±r), the ellipse, and polygon `points` in the bbox. Hash the geometry of non-path primitives into `path_hash`, or add a separate shape hash.

### M3. Duplicate element ids collapse in drift comparison and in assertions
- **Severity:** medium
- **Where:** `tools/run_tests.py:435-436` (`{el["id"]: el ...}`) and `:529-531`
- **Defect:** Multi-system scores produce several `staff-symbol` elements; `example-notes` and both `joy-to-the-world` scores have 4 each, and the `joy` scores also have 2 elements called `ll-1-0.000-0`. Keying by id keeps only the last one. The other systems' staff-symbol elements, and the first ledger spanner, are never compared or asserted.
- **Failure scenario:** Systems 1-3 of a multi-system score change width or x position. The `systems` block records only y geometry and measures, so nothing fails.
- **How verified:** In `tests/joy-to-the-world.harvested.json` I moved the first `staff-symbol` 10 points right, widened it by 25, and moved the first `ll-1-0.000-0` 3 points down. `harvest_differences` returned `[]`.
- **Fix:** Make ids unique in `cnb/test-ids.ly` by adding a system index or a counter, and have `harvest_differences` (and the runner) fail on duplicate ids rather than silently dropping them.

### M4. `CNB_LILYPOND_X_Y` is trusted without a version check, so a "2.26" suite can silently run 2.24
- **Severity:** medium
- **Where:** `tools/run_tests.py:326-327` (pinned by `tools/test_run_tests.py:118-122`, `run.assert_not_called()`)
- **Defect:** When the variable is set, `resolve_lilypond` returns it without running `--version`. Only the PATH fallback is checked.
- **Failure scenario:** The variable is stale or mis-set, for example pointing at a 2.24 install. `engine-unit-2.26` passes on 2.24 and reports a 2.26 proof. `engine-integration-2.26` fails, but only as harvest drift, so the cause is misreported.
- **How verified:** I set `CNB_LILYPOND_2_26` to the 2.24 `lilypond`. `run_unit.py --lilypond-version 2.26` printed `UNIT RESULTS: 303 passed, 0 failed` and exited 0.
- **Fix:** Run `lilypond_version()` on the variable's executable too, and exit naming the variable when the result is not X.Y. Update the test that asserts no subprocess call.

### M5. A wrong path, or running from another folder, yields "No test specs found" with exit 0
- **Severity:** medium
- **Where:** `tools/run_tests.py:740` (default `"tests/"` is relative to the current directory) and `:750-755` (`sys.exit(0)`)
- **Defect:** Missing paths are only warned about. An empty spec list exits successfully.
- **Failure scenario:** A typo such as `run_tests.py tests/c-major.json` (the docstring's own example names a file that does not exist), or a CI or router step running from `tools/`, passes having tested nothing. `run_unit.py` uses `PROJECT_ROOT` and does not have this problem.

### M6. The advertised articulation correction never changes anything, and the beam and stem compensation never apply on the engine's own staff
- **Severity:** medium
- **Where:** `cnb/articulations.ly:120-127`, `cnb/beams.ly:50`, `cnb/stems.ly:125`. Features advertised at README.md:61.
- **Defect:**
  - **Articulations.** The proximity rule only produces ledger lines between the note and the staff. So `diff = |extreme ledger| - |note|` is never at least 2, and `adjust` is always 0. Also, for a single-note column the Script's X-parent is the NoteColumn, whose staff position is 0.
  - **Beams and stems.** The compensation runs only when `staff-space < 1.0`, and the engine never sets `staff-space`.
- **Failure scenario:** A staccato or accent next to the ledger lines of a far-out note gets no correction. The engraving-correction features advertised in the README do nothing unless the user overrides StaffSymbol.staff-space themselves.
- **How verified:**
  - **Articulations.** I logged the callback (`probe/art-log.ly`) for notes at positions -17 through 19, with the X-parent being NoteHead and NoteColumn: the result equalled the default in every call. I also enumerated `cnb:proximity-rule` for positions -40..40 in both directions (`probe/prox.ly`): there was no nonzero adjustment.
  - **Beams.** I multiplied the beam thickness inside the `(< ss 1.0)` branch by 3, and the full integration run gave an identical SVG and harvest for every test.
- **Fix:** Either fix the articulation logic (measure the clearance against the actual ledger extent, and read the NoteHead rather than the NoteColumn), or remove it and the README claim. Either document that beam and stem compensation apply only to a user-shrunk staff-space, or drop them.

### L6. The absence convention passes a missing element for any expression containing `is None`
- **Severity:** low
- **Where:** `tools/run_tests.py:554-566`
- **Defect:** If the element is missing and any expression contains `"is None"` or `"== None"`, the whole assertion passes, including the assertion's other properties and expressions about other elements. An assertion with an empty `expect` passes whenever the element exists.
- **Failure scenario:** A spec author writes `{"visual.color": ["v is None"], "type": ["== 'notehead'"]}`, meaning "uncoloured notehead". It passes when the notehead is not rendered at all.
- **How verified:** I read the code. No current spec is affected: all the specs' absence checks are the pure `type: ["is None"]` form, which my script confirmed.
- **Fix:** Require an explicit marker such as `"absent": true`, and fail an assertion whose `expect` is empty.
