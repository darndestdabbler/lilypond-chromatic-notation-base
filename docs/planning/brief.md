# Brief — wrap-up program for `lilypond-chromatic-notation-base`

> Written 2026-10-30 from the operator-approved wrap-up plan for the four
> chromatic-notation repositories. Session 1 imports this into
> `docs/planning/project-plan.md` (amend that file; do not create a
> `solution-plan.md`). Session 2 breaks §4 below into numbered sessions.

## 1. Objective

Finish, clean up and document the CNB engine to the level of "reliable for
simple exploration", as the last stage of a three-tool pipeline
(`inkscape-music-glyph-toolkit` → `chromatic-notation-configurator` → this
engine), then release it as **1.0.0** and make the repository public under
CC0.

Out of scope: new engine features, new configuration models, the deferred
items in `project-plan.md` §3 ("Deferred / explicitly out of scope"), and
support for LilyPond versions other than 2.24.x (E2 only records what a newer
version does).

Success: from a fresh clone on a stock Windows console, the unit and
integration suites run green with no environment variables set and leave the
working tree unchanged; the README's figures and status match reality; a
1.0.0 tag exists.

## 2. Production split and handoff

One module: the repository itself, a tree of LilyPond/Scheme files loaded by
`ChromaticNotationBase.ly`, plus Python 3.8+ test tooling under `tools/`. It
reaches no database. It is handed over as the source tree (users clone it and
`\include` a config); the release is an annotated `v1.0.0` tag
(`packaging: release: tag`), published by the operator pushing the tag.

## 3. State on 2026-10-30

- All eight session sets complete; every Configurator coordination item in
  `docs/planning/configurator-coordination-backlog.md` is resolved.
- `test-unit.ly`: 303 assertions pass. LilyPond exits 0 even on failure, so
  it is not declared as a suite.
- `tools/run_tests.py`: 246 tests / 349 assertions pass, but only with
  `-X utf8` or `PYTHONUTF8=1`; on a stock cp1252 console it crashes with
  `UnicodeEncodeError` on its banner before running anything.
- Every run rewrites the tracked `tests/*.svg`; the point-and-click
  `textedit://` links embed the absolute path, so a run from a differently
  cased or located checkout dirties the tree.
- README figures are stale (says 179 unit + 231 integration assertions).
- `tests/TODO.md`: `example-notes` has a harvest but no assertion spec.
- Cruft: `tools/old/`, `tools/to-transition-to-python/`, a committed
  `test-unit.pdf`.
- Pinned to LilyPond 2.24.2; newer versions untested.

## 4. Work (sessions 3 onward)

1. In `tools/run_tests.py` and `tools/harvest_svg.py`, reconfigure stdout to
   UTF-8 (or fall back to ASCII) and open files with explicit encodings;
   render with `-dno-point-and-click` (or write rendered SVGs and harvests to
   an ignored output folder) so a run never modifies tracked files; warn when
   LilyPond is not 2.24.x.
2. Add `tools/run_unit.py`: runs `lilypond test-unit.ly` into an ignored
   output folder, parses `TEST RESULTS: N passed, M failed`, and exits

   a second suite (`command:` form), and drop `-X utf8` from the integration
