Session 8: Let the test runners choose a LilyPond version

Why. 1.0.0 supports LilyPond 2.24.x only, and 2.26 is the current stable release, so a new user is likely to have it. Measured on 2026-10-31 in a scratch worktree: with the session 9 fixes, every engine-unit and engine-integration assertion passes on 2.26.0, but 11 of the tracked harvests differ in layout coordinates. Supporting both versions needs a harvest baseline set per version, and suites that prove each one. On the operator's machine 2.24.2 is on PATH and 2.26.0 is at D:\lilypond-2.26.0-mingw-x86_64\lilypond-2.26.0\bin\lilypond.exe, named by the user environment variable CNB_LILYPOND_2_26.

  1. Register.
  2. Give tools/run_tests.py and tools/run_unit.py a --lilypond-version X.Y option. It uses the executable named by CNB_LILYPOND_X_Y (dots become underscores), or else the lilypond on PATH if its --version reports X.Y. Otherwise it exits non-zero with a message naming the variable to set. Without the option, both behave as today. The supported set is 2.24 and 2.26. The 2.24 harvest baselines stay at tests/*.harvested.json, and 2.26's go in tests/lilypond-2.26/. For any version other than 2.24, renders go to the ignored out/lilypond-X.Y/, so the tracked tests/*.svg are never rewritten by a 2.26 run. For a version outside the supported set, warn and skip the drift comparison; assertions still run. Replace the "baselined on 2.24" warning with this. Tests in tools/test_run_tests.py cover: resolution from the variable, from PATH, and the failure message; the baseline path for 2.24 and for 2.26; and the unsupported-version skip. Prove it by running the engine-tooling suite, then python tools/run_tests.py --lilypond-version 2.24 and python tools/run_unit.py --lilypond-version 2.24. Both pass, and git status -- tests is clean.
  3. Add --lilypond-version 2.24 to the engine-integration and engine-unit suite commands in dabbler.yaml, so the run of record names the version it proves.

Work Plan

Give tools/run_tests.py and tools/run_unit.py a --lilypond-version X.Y option. run_tests.py gains small helpers that both runners use: the variable name for a version (CNB_LILYPOND_X_Y), the version a lilypond executable reports (X.Y from the first line of --version), resolution of the executable (the variable's value, else the lilypond on PATH if it reports X.Y, else exit non-zero with a message naming the variable to set), the render directory (out/lilypond-X.Y/ for any version other than 2.24, so tracked tests/*.svg are never rewritten by such a run) and the harvest baseline directory (beside the spec for 2.24, tests/lilypond-2.26/ for 2.26, none for a version outside the supported set {2.24, 2.26}). The LilyPond executable is passed to run_lilypond instead of the hard-coded name. For an unsupported version run_tests.py warns once and skips the drift comparison while every assertion still runs; this replaces the old 'baselined on 2.24' warning, which is removed. Without the option both runners behave as today: lilypond from PATH, renders beside the spec (run_unit.py into out/), drift compared with tests/*.harvested.json. Tests in tools/test_run_tests.py cover resolution from the variable, from PATH, and the failure message; the baseline path for 2.24 and 2.26; and the unsupported-version skip. Then dabbler.yaml's engine-integration and engine-unit suite commands gain --lilypond-version 2.24 so the run of record names the version it proves.
