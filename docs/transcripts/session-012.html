Session Plan

Session 12: Engrave durations and dots correctly

Why. A whole-repository audit on 2026-11-02 (docs/planning/audit-2026-11-02.md; finding IDs below refer to it) found visible engraving errors that every suite passed:

  • cnb:duration-category is computed from the full duration length, so dots and tuplets change the category (H2).
  • It is off by one against the engine's own documented scale in cnb/procedure.ly: 0 = breve or longer, 1 = whole, 2 = half, 3 = quarter or shorter. The scale is also the export spec's, so a Configurator rule for minims hollows quarter notes (Configurator audit H4).
  • Dots on ledger-line notes land 6–8 staff spaces away (H3).
  1. Register.
  2. Compute the category from the duration *log* alone, as clamp(log + 1, 0, 3). That maps breve → 0, whole → 1, half → 2, and quarter or shorter → 3, ignoring dots and the tuplet factor. Update every consumer to that scale: noteheads.ly (repeat counts must still give 2 heads for a half and 4 for a whole), off-key.ly, stems.ly, stencils.ly and the cache key. Add unit tests to test-unit.ly for every duration log from −1 to 4, with and without dots, for triplets, and for the cache key.

Add an integration spec, tests/duration-rules.ly plus its .json. It uses a small config whose procedure gives each category a different colour, and engraves a breve, a whole, a half, a quarter, an eighth, dotted versions and triplets. It asserts the colour and head count of each note.

  1. H3: in cnb/dots.ly, count the notehead offset once. Add an integration spec with dotted notes on and off ledger lines above and below the staff, asserting each dot's distance from its notehead.
  2. M1: stem attachment uses the config the note was engraved with, not the global cache at layout time, so a later \key change no longer rewrites earlier stems. Add a spec with a key-dependent config and a mid-score key change.

Run all five suites. Where an existing harvest drifts, re-baseline it with --update-baselines on both versions only after checking that every difference is one of these three fixes. Record each re-baselined file and why in §7.7 of docs/planning/project-plan.md.
